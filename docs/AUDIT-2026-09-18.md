# Render-path audit — 2026-09-18

Read-only audit of the per-frame path: `App/Sources/Videoboy/Render/Engine.swift`,
`Core/Sources/VideoboyCore/Graph/*`, every `Node` under `Core/.../Modules/`, the
output/record/stream paths, and the control threads that write into them.

No file outside this one was modified. No builds or tests were run; every claim below
is from reading the current source, and every line reference was checked against it.

Priority framing follows `CLAUDE.md`: **the worst frame is what matters.** A finding
that costs 200 ms once every ten minutes is ranked above one that costs 2 ms every
frame, because the first drops frames and the second does not.

---

# CONFIRMED

## C1 — `FeedbackNode` rebuilds its entire ring buffer whenever the delay parameter moves

**Critical.** `Core/Sources/VideoboyCore/Modules/Effects/FeedbackNode.swift:108-116`

```swift
let requiredSize = delayFrames + 2
if ringSize != requiredSize || ring.first??.width != width || ... {
    ring = (0..<requiredSize).map {
        metal.makeRenderTarget(width: width, height: height, label: "\(identifier)-ring\($0)")
    }
    ...
}
```

`delayFrames` is a registry parameter with range `0...60`
(`FeedbackNode.swift:42-46`, `:55`), pulled from the registry every frame by
`applyParameters` (`:191-193`) via `Int(value.rounded())`. So `requiredSize`
changes whenever the fader crosses a rounding boundary.

Each `makeRenderTarget` is not a cheap allocation. `MetalContext.makeRenderTarget`
(`Core/.../SelfQA/MetalContext.swift:871-897`) deliberately clears every new target,
and `clearToBlack` (`:900-914`) commits a render pass and calls
`waitUntilCompleted`. The comment there says "the cost is one pass at allocation —
on resize, not per frame." That premise is false for this node: the ring resizes on a
*parameter* change, not a geometry change.

**What goes wrong.** One frame where the delay moves from 59 to 60 destroys and
rebuilds 62 render targets: ~86 MB of texture allocation and **62 serialized GPU
round trips**, all inside one `tick`. Expect hundreds of milliseconds. There are six
`FeedbackNode`s in the graph (one per channel plus one per bus,
`Engine.swift:214-215`, `:239`, `:278`), so a mapping that moves several at once
multiplies it.

**Trigger sequence.**
1. Arm bus ONE's feedback (`wetDry > 0.001`, or the ring code never runs).
2. Drag the DELAY fader across its travel, or map an LFO to
   `ParamCode.feedbackDelayFrames`.
3. Every frame where the rounded value changes rebuilds the ring.

**When it bites.** The first time anyone touches that control — so a few minutes into
the first real session, not four hours. Under an LFO it is *every frame, forever*:
a sustained allocate-and-free of tens of megabytes of Metal textures per frame,
which is also the fastest route to VM/IOSurface fragmentation in this codebase.

**Suggested fix.** Allocate the ring once at `maximumDelayFrames + 2` and treat
`delayFrames` purely as a read offset — the read already wraps modulo `ringSize`
(`:128`), so nothing else has to change. 62 SD targets is ~86 MB held steady per
node, which is real; if that is too much, cap the ring at a smaller fixed size and
clamp the delay to it, or grow-only (never shrink) so the reallocation happens at
most `maximumDelayFrames` times in a session. Do not reallocate downward.

## C2 — A fresh `AVAssetReader` is constructed on the render thread, once per frame, whenever a clip plays backwards

**Critical.** `Core/Sources/VideoboyCore/Modules/Sources/AVFClipDecoder.swift:100-102`
and `:129-159`; ping-pong at
`Core/Sources/VideoboyCore/Modules/Sources/ClipSourceNode.swift:450-459`.

```swift
if wrapped < nextFrameIndex || wrapped > nextFrameIndex + Self.maximumForwardScan {
    guard restartReader(atFrame: wrapped) else { return nil }
}
```

`restartReader` cancels the old reader, builds a new `AVAssetReader`, adds a track
output, sets a `timeRange`, and calls `startReading()` — all synchronously, on the
render thread, from inside `ClipSourceNode.render`.

**The backwards case.** Ping-pong reverses the playhead at the out point
(`ClipSourceNode.swift:453-455`). Travelling backwards, the 48-frame cache
(`AVFClipDecoder.swift:35`) covers the first 48 frames of the return trip. After
that, every frame is a cache miss *and* satisfies `wrapped < nextFrameIndex`,
because the previous restart set `nextFrameIndex = wrapped` and then decoded one
frame forward. So:

- frame *N*: miss → restart at *N* → decode 1 → `nextFrameIndex = N+1`
- frame *N−1*: miss → `N−1 < N+1` → restart at *N−1* → decode 1 → …

**One `AVAssetReader` construction per displayed frame, for the entire backward half
of the loop.** Worse, the `timeRange` start (`:147`) is an arbitrary frame, not a
keyframe, so each new reader must decode from the preceding keyframe — on H.264
with a two-second GOP that is ~60 decoded frames to produce one displayed frame.

**The loop case.** At a wrap, `wrapped` goes to 0 while `nextFrameIndex` is at the
clip end, so `wrapped < nextFrameIndex` and the reader restarts. One guaranteed
long frame at every loop point. A ten-second clip wraps 1,440 times in four hours.

**When it bites.** Ping-pong: about 1.6 seconds after the turn, on any clip longer
than ~96 frames. Loop: at the first wrap. Neither shows up in a short test unless
the tester happens to leave a clip running past its end in the right loop mode.

**Suggested fix.** Two parts, independent.
- *Never build a reader on the frame path.* Do the restart on a decode queue and let
  `render` return the last good texture until the new reader has produced the wanted
  frame. `ClipSourceNode.render` already has the "hold the last picture" branch
  (`:550-555`) — this is the same degradation, on purpose.
- *Make backwards playback not need restarts.* When `isPlayingBackwards` is set,
  decode a block forward from `wrapped - cacheSize` in one pass and serve the
  following frames out of the cache. That turns one restart per frame into one per
  48 frames. Fixing C13 first makes the existing cache actually hold 48 frames,
  which is a prerequisite for either approach being effective.

## C3 — `OffscreenRenderer.readback` allocates a staging texture and makes three full-frame CPU passes, per call, on the frame path

**Critical under sustained load.**
`Core/Sources/VideoboyCore/SelfQA/OffscreenRenderer.swift:39-81`.

The name and the file's location say "self-QA". It is not: it is on the live frame
path in four places.

```swift
public func readback(_ texture: MTLTexture) -> ImageBuffer? {
    let stagingDescriptor = MTLTextureDescriptor.texture2DDescriptor(...)   // :43
    guard let staging = context.device.makeTexture(descriptor: stagingDescriptor), // :48
    ...
    commandBuffer.waitUntilCompleted()                                       // :64
    var bgra = [UInt8](repeating: 0, count: width * height * 4)              // :71
    ...
    return ImageBuffer.fromBGRA(width: width, height: height, bgra: bgra)    // :80
}
```

Per call: one fresh `.shared` `MTLTexture` (1.38 MB at SD), one blocking GPU round
trip, one 1.38 MB array allocation, then `ImageBuffer.fromBGRA`
(`Core/.../SelfQA/ImageBuffer.swift:139-145`) which copies the array *again* and runs
a per-pixel swap loop. Nothing is cached between calls — not the staging texture,
not the byte buffer.

**Frame-path callers.**

| Caller | Rate |
|---|---|
| `App/.../Platform/RecordingSession.swift:85-92` | once per armed feed, **every frame** — up to 7 |
| `App/.../Output/OutputRouter.swift:328-333` | once per streaming destination, **every frame** |
| `Core/.../Modules/Effects/BusCodecNode.swift:127-128`, `:148` | once per bus with interchange active, **every frame** — up to 3 |
| `App/.../UI/ShellController.swift:1815-1817` | up to 3, every 5th frame (this one is paced, and fine) |

Recording all seven feeds with DV interchange on all three buses is **ten readbacks
per frame**: ten new `.shared` textures, ten GPU stalls, twenty full-frame CPU
allocations and ten swizzle loops — before `FrameRecorder` adds its own (C14).

**When it bites.** Recording is the four-hour scenario by definition. The allocation
churn is ~14 MB/frame of short-lived `.shared` textures at 29.97 fps — about
400 MB/s through the allocator, which is where IOSurface and wired-memory
fragmentation comes from over a long run.

**Suggested fix.** Cache the staging texture and the destination byte buffer on the
`OffscreenRenderer` instance, keyed on size, exactly as the effect nodes cache their
render targets. Then give the recorder and the streamer a BGRA-native readback that
skips `fromBGRA` entirely (see C12/C14 — all three are the same mistake). If
recording needs to stay fast after that, the readback belongs behind a
`addCompletedHandler` rather than `waitUntilCompleted`, with the encode on its own
queue.

## C4 — Turning the test pattern OFF rebuilds three bus codecs and loses the crossfader

**High.** `App/Sources/Videoboy/Render/Engine.swift:923-944`.

```swift
func setProgramShowsTestPattern(_ showsPattern: Bool) {
    guard showsPattern != programShowsTestPattern else { return }
    programShowsTestPattern = showsPattern
    if showsPattern {
        graph.connect(from: Engine.testPatternSlot, to: GraphTopology.primary, inputIndex: 0)
        registry.setValue(0, slot: GraphTopology.primary, code: .crossfadeOneTwo)   // :928
    } else {
        busCodecOne = BusCodecNode(identifier: Engine.busCodecOneSlot, context: metal)    // :933
        busCodecTwo = BusCodecNode(...)                                                    // :934
        busCodecProgram = BusCodecNode(...)                                                // :935
        graph.add(busCodecOne); graph.add(busCodecTwo); graph.add(busCodecProgram)
        graph.connect(from: Engine.mx1OneSlot, to: Engine.busCodecOneSlot, inputIndex: 0)
        graph.connect(from: Engine.busCodecOneSlot, to: GraphTopology.primary, inputIndex: 0)
    }
}
```

The else branch is verbatim copy-paste from `buildGraph` (`:258-269`), comment
included, mis-indented. Four separate defects:

1. **The crossfader is never restored.** `:928` writes `crossfadeOneTwo = 0` on the
   way in; nothing writes it back. After one round trip, PROGRAM carries bus ONE
   only and the ONE/TWO fader appears dead until it is touched. This is the most
   likely thing an operator actually notices.
2. **The scheduler's subscriptions are orphaned.** `buildSchedule` (`:502-508`)
   captures the three codec objects **strongly** in its `.quarter` closures. Replacing
   `Engine.busCodecOne` replaces the *engine's* reference; the closure still holds
   the old object. So: bus data effects stop re-rolling on the beat, permanently,
   and the three dead nodes (with their `DVEncoder`, `DVDecoder`,
   `previousEncodedFrame` and cached textures) are retained forever by the
   scheduler. Every toggle leaks another three.
3. **Node state is lost.** `interchange` is a plain property set by
   `setInterchange` (`:810-816`), not a registry value, so the fresh nodes come up
   at `.none`. Meanwhile `isOutputDVEnabled`'s getter reads the *registry*
   (`:888`), so the UI reports DV ON while the node does nothing — the same
   switch-disagrees-with-engine class of bug the `busEffectSlots` comment at
   `:456-463` was written to prevent.
4. **`graph.registerParameters` is not re-run.** Harmless today only because
   `RenderGraph.add` replaces by identifier and the slot names are unchanged, so
   `applyAllParameters` still finds them. It is load-bearing by accident.

**When it bites.** Second toggle of the test pattern — minutes, during calibration,
which is exactly when someone is toggling it.

**Suggested fix.** The else branch should be two lines: reconnect
`mx1OneSlot → busCodecOneSlot → primary[0]` and restore the saved
`crossfadeOneTwo` value captured on the way in. Delete the three constructions
entirely. Separately, `buildSchedule` should look the node up through the engine
(`self?.busCodecOne`) rather than capturing the instance, so no future swap can
orphan it the same way.

**Correction to the lead as given:** the lead said the else branch reconstructs the
nodes "instead of restoring the mix routing." The routing edges *are* restored
(`:940-941`), and `busCodecTwo`/`busCodecProgram`'s edges were never removed, so
the topology survives. The damage is the lost crossfader, the orphaned
subscriptions, and the lost node state — not a broken graph.

## C5 — `Log.emit` does a synchronous stderr write from the render thread, with unbounded call sites

**High.** `Core/Sources/VideoboyCore/Logging.swift:76-84`.

```swift
private static func emit(...) {
    ...
    lock.lock(); ring.append(line); ...; lock.unlock()
    if shouldEcho { FileHandle.standardError.write(Data((line.formatted + "\n").utf8)) }
}
```

The file's own header says "this is not on the hot path of the render loop"
(`:54-55`). It is. `FileHandle.write` is a blocking `write(2)`. When stderr is a pipe
— launched from a terminal, from Xcode, from any log collector — and the reader is
slow, the 64 KB pipe buffer fills and **the render thread blocks until it drains**.
That is an unbounded stall on the frame path with no upper limit.

Per-frame call sites that can fire indefinitely:

- `ClipSourceNode.swift:553` — `Log.warn(.dv, ...)` every frame a clip fails to
  decode. A truncated or unsupported file produces 29.97 lines/sec: **432,000 lines
  and ~30 MB of stderr over four hours**, each line a syscall on the render thread.
- `Engine.swift:496`, `:506` — one `Log.info(.clock, ...)` per scheduled event.
  Seven subscriptions at `.quarter`, 120 BPM = 14 lines/sec, ~200,000 over four hours.
- `ParamRegistry.setValue:148` — warns on every unresolved slot/code. An LFO or
  mapping pointing at a code a node no longer exposes logs once per frame, forever.
- `RenderGraph.evaluationOrder:90` — "cycle detected" logs per visit, per frame, for
  as long as a cycle exists.

**When it bites.** With a bad clip, 20 minutes is already a 400 MB log and a visibly
degraded frame rate. With everything healthy, the scheduler chatter alone makes
four hours unpleasant.

**Suggested fix.** Two changes, both small.
- Take the stderr write off the caller's thread: hand formatted lines to a serial
  `DispatchQueue` (or an `os_log` handle, which is designed for this). The ring
  buffer under the lock can stay — it is bounded and cheap.
- Rate-limit or de-duplicate the per-frame call sites. `ClipSourceNode:553` in
  particular should log the *transition* into the no-picture state, not the state.
  A `lastLoggedFailureFrame` guard is enough.

## C6 — `MPEGTSStreamer.send` encodes and writes to a socket on the render thread

**High.** `Core/Sources/VideoboyCore/Bitstream/MPEGTSStreamer.swift:167-215`, called
from `App/.../Output/OutputRouter.swift:333`, called from
`ShellController.refresh` (`:2266`), called from `Engine.tick`.

Per streamed frame, on the render thread: a full-frame array copy (`:176`,
`var pixels = image.pixels`), an `sws_scale` RGBA→YUV420P conversion, an MPEG-2
encode, and `av_interleaved_write_frame` (`:209`) — a blocking socket write.

`CLAUDE.md` is explicit: *"no synchronous file or network I/O, ever"* on the render
path. This is both. A UDP send to a host that is not draining, or a TCP target that
applies backpressure, blocks `tick` directly.

The comment at `OutputRouter.swift:329-331` acknowledges the cost ("a full CPU
readback and an MPEG-2 encode per frame. Not free") and justifies it on the grounds
that it only happens while streaming. That justifies the *CPU* cost. It does not
address the blocking write, which has no bound at all.

**When it bites.** Immediately on opening a stream route, and gets worse as the
receiver's behaviour degrades — an OBS instance that stalls takes the instrument
down with it.

**Suggested fix.** Move the encode and the write to a dedicated serial queue with a
depth-1 mailbox: the render thread drops the latest `ImageBuffer` in and returns;
the queue encodes whatever is there and drops frames if it falls behind. Dropping a
streamed frame is correct — `FrameRecorder.write` already makes exactly this
argument for the recorder (`FrameRecorder.swift:194-196`) and the streamer should
follow it.

## C7 — `Scheduler.firedEvents` grows without bound

**Medium.** `Core/Sources/VideoboyCore/Clock/Scheduler.swift:59`, `:152`.

```swift
private(set) public var firedEvents: [ScheduledEvent] = []      // :59
...
for (subscription, event) in due {
    firedEvents.append(event)                                    // :152
    subscription.action(event)
}
```

`resetHistory()` (`:165`) has no caller outside tests.

**Quantified.** `buildSchedule` (`Engine.swift:491-509`) creates seven subscriptions
— four sources and three bus codecs — all at `.quarter`. At 120 BPM that is 2
boundaries/sec × 7 = **14 events/sec**.

| Runtime | Events | Array bytes |
|---|---|---|
| 20 min | 16,800 | ~540 KB |
| 4 h | 201,600 | ~6.5 MB |

`ScheduledEvent` is `Int` + three `Double` = 32 bytes. The steady memory is modest;
the sharp edge is **array growth**. Swift doubles capacity, so the last few
reallocations copy 3 MB, then 6.5 MB — a single-frame memcpy spike on the render
thread at unpredictable moments. About eighteen such doublings over four hours.

At `.sixteenth` — which is what the lead asked about, and what `beatSubdivision`
(`Engine.swift:824`) implies the app intends to offer — it is 4× everything:
**806,400 events, ~26 MB, with a 26 MB memcpy on one frame.** Note that
`beatSubdivision` is currently *not* wired to any subscription (see S5), so 1/16 is
not reachable today; it becomes reachable the moment that is fixed.

**Suggested fix.** Make `firedEvents` a bounded ring — 256 entries is more than the
debug overlay or any test needs. `Log`'s own ring (`Logging.swift:58-59`) is the
pattern to copy. Do not simply call `resetHistory()` from the run loop; a ring has no
periodic spike.

## C8 — `AudioInput.consume` allocates and does `O(n)` work on the audio render thread

**Medium.** `App/Sources/Videoboy/Platform/AudioInput.swift:123-163`.

Everything below runs inside the `installTap` block (`:92-94`), which CoreAudio calls
on a real-time thread where allocation, locking and logging are all forbidden:

- `:134` `pending.reserveCapacity(...)` — can reallocate.
- `:140` `pending.append(...)` per sample — can reallocate.
- `:145` `Array(pending[0..<windowSize])` — a fresh allocation per window.
- `:146` `pending.removeFirst(windowSize)` — `O(n)` memmove of the remainder.
- `:149` `onFrame?(frame)` → `Engine.swift:771-778`, which does a
  **`DispatchQueue.main.async` per window**.
- `:161` `Log.warn(...)` — takes a lock and (per C5) does a blocking stderr write,
  from the audio render thread.

The main-queue hop is the unbounded one. At 44.1 kHz with a 1024-sample window that
is ~43 blocks/sec, each retaining an `AudioFrame`. When the main thread is busy —
which, since `tick` runs there, is most of the time, and *entirely* the case during
a C1 ring rebuild or a C2 reader restart — these queue up with no backpressure.
`onTempo` (`:152-154`, `Engine.swift:779-783`) adds a second unbounded stream.

**When it bites.** Whenever the audio clock is on and the main thread has a bad
frame. The audible symptom is an audio glitch; the visible one is a main queue
backlog that arrives as a burst of parameter changes.

**Suggested fix.** Replace `pending` with a preallocated fixed-size ring buffer and
index arithmetic — no allocation, no `removeFirst`, no per-sample append. Drop the
`Log.warn` or route it through a lock-free counter read elsewhere. Coalesce the main
hop: store the latest `AudioFrame` in an atomic slot and let the *render tick* read
it, rather than posting a block per window. The engine already reads audio state
once per frame; it does not need 43 deliveries per second.

## C9 — `AudioInput.stop()` races the audio thread

**Medium.** `App/Sources/Videoboy/Platform/AudioInput.swift:111-120`.

```swift
func stop() {
    engine.inputNode.removeTap(onBus: 0)
    engine.stop()
    isRunning = false
    analyzer?.reset()        // :116
    tempoEstimator?.reset()  // :117
    pending.removeAll()      // :118
}
```

Called from the main thread (`Engine.setClockSource:762`, `Engine.stop:526`).
`removeTap` does not guarantee that an already-dispatched tap block has returned, so
`consume` can be mid-flight in `pending.append` (`:140`) while main calls
`pending.removeAll()` (`:118`) — concurrent mutation of a Swift `Array`, which is
memory-unsafe, not merely lossy. Same for `analyzer.reset()` against
`analyzer.analyze(...)` at `:148`.

**When it bites.** Any switch from the audio clock back to internal. Rare and
timing-dependent, which is why it survives short testing; it is the kind of thing
that crashes once in a set and is never reproduced.

**Suggested fix.** Guard the shared state with the same lock-free ring from C8, or
gate `consume` on an atomic `isRunning` flag that `stop()` clears *before*
`removeTap`, then let the ring drain naturally rather than clearing it. `pending`
should only ever be touched by the audio thread.

## C10 — `MIDIInput.connectedSourceNames` is written from a CoreMIDI thread and read from main

**Medium.** `Core/Sources/VideoboyCore/Control/MIDIInput.swift:39`, `:100-116`.

`connectAllSources()` writes `connectedSourceNames` at `:114`. It is called from two
places: `start()` at `:95` (main thread, fine) and the `MIDIClientCreateWithBlock`
notification block at `:73-76`. `MIDIClientCreateWithBlock` — unlike
`MIDIClientCreate` — invokes its block on an internal CoreMIDI thread, not the
client's run loop. The read is on main:
`App/.../UI/ShellController.swift:2308`, inside the once-a-second status block, so
inside `tick`.

An unsynchronised `[String]` write concurrent with a read is a data race: the array's
buffer pointer and count are not updated atomically, and the strings are
reference-counted, so a torn read can over-release. The window is narrow but the
failure is a crash, not a wrong label.

**When it bites.** A controller plugged in or unplugged mid-show, or a virtual source
appearing. Once in a long session; never in a five-minute test.

**Suggested fix.** Hop the notification block's body to main
(`DispatchQueue.main.async { self?.connectAllSources() }`), which also makes
`MIDIPortConnectSource` calls serial with everything else touching the port. That is
a one-line change and matches what `:225` already does for events.

## C11 — One unbounded `main.async` per MIDI word, capturing `self` strongly

**Medium.** `Core/Sources/VideoboyCore/Control/MIDIInput.swift:214-231`.

```swift
for wordIndex in 0..<Int(packet.wordCount) where wordIndex < words.count {
    if let event = Self.decode(word: words[wordIndex]) {
        DispatchQueue.main.async { self.handle(event: event) }   // :225
    }
}
```

Two problems. The outer closures at `:73` and `:84` are correctly `[weak self]`;
this inner one captures `self` **strongly**, so every in-flight block keeps the
`MIDIInput` — and through it the `ParamRegistry` — alive. More importantly there is
no coalescing: a motorised fader or an LFO on a CC streams hundreds of messages per
second, each becoming its own main-queue block. When the main thread is stalled
(C1, C2, C5, C6 all do this), the queue grows without bound, and when it drains the
parameter lands wherever the *last* queued message says — after a visible lag.

**When it bites.** Any dense CC source. Minutes, not hours, on a controller with
motorised faders.

**Suggested fix.** Capture `[weak self]`. Then coalesce: accumulate decoded events
into a lock-protected "latest value per `ControlSource`" dictionary on the CoreMIDI
thread and drain it once per frame from `tick`, before `applyAllParameters`. That
gives one main-thread hop per frame instead of one per message, and it is the
correct semantics anyway — nothing downstream can use more than one value per
parameter per frame.

## C12 — BGRA → RGBA → BGRA: two full-frame CPU swizzles to reach the format AVFoundation already gave us

**Medium.** `Core/.../Modules/Sources/AVFClipDecoder.swift:168-195` and
`Core/.../SelfQA/MetalContext.swift:1031-1034`.

`restartReader` asks AVFoundation for `kCVPixelFormatType_32BGRA`
(`AVFClipDecoder.swift:138-139`), with a comment saying "BGRA because that is what
Metal and ImageBuffer both want; letting AVFoundation convert is faster and more
correct than doing it here."

Then `imageBuffer(from:)` (`:169-195`) immediately allocates
`[UInt8](repeating: 255, count: width * height * 4)` and runs a scalar per-pixel loop
converting that BGRA to RGBA — 345,600 iterations per SD frame.

Then `MetalContext.makeTexture(from:)` (`:1031-1034`) does:

```swift
var bgra = image.pixels            // full-frame COW copy
for index in stride(from: 0, to: bgra.count, by: 4) { bgra.swapAt(index, index + 2) }
```

…converting it straight back to BGRA, because `MetalContext.pixelFormat` is
`.bgra8Unorm` (`:806`). Three allocations and two full-frame scalar passes per
channel per frame, to end where AVFoundation started.

At four channels, 29.97 fps, this is a meaningful slice of the 11.4 ms worst-case
figure `CLAUDE.md` records, and `CLAUDE.md` forbids exactly this ("no CPU pixel
loops").

Note the same pattern recurs twice more, independently: `ImageBuffer.fromBGRA`
(`ImageBuffer.swift:139-145`) in C3, and `FrameRecorder.write` in C14.

**When it bites.** Continuously. Not a long-runtime bug — a permanent tax on the
headroom that protects against the long-runtime bugs.

**Suggested fix.** The cleanest version is to stop round-tripping through
`ImageBuffer` for AVFoundation clips at all: wrap the `CVPixelBuffer` with a
`CVMetalTextureCache` and hand the resulting `MTLTexture` straight to the graph —
zero copies, zero CPU passes. There is no `CVMetalTextureCache` anywhere in the repo
today; this is where it earns its keep.

If `ImageBuffer` must stay in the path (the DIF corruptor needs CPU bytes, so the DV
path genuinely does), then at minimum: give `ImageBuffer` a `isBGRA` flag, have
`imageBuffer(from:)` do a straight `memcpy` per row, and have `makeTexture(from:)`
skip the swizzle when the flag is set. One `memcpy`, no scalar loops.

## C13 — `store()` appends duplicate indices to `cacheOrder`, shrinking the effective cache

**Medium.** `Core/.../Modules/Sources/AVFClipDecoder.swift:197-203`.

```swift
private func store(_ frame: ImageBuffer, at index: Int) {
    cache[index] = frame
    cacheOrder.append(index)
    while cacheOrder.count > Self.cacheSize {
        cache.removeValue(forKey: cacheOrder.removeFirst())
    }
}
```

`cacheOrder` is append-only with no dedupe. When a frame already in the cache is
re-decoded — which happens in the forward-scan loop at `:104-116`, and after every
restart — its index is appended a second time. Eviction then pops the *oldest*
occurrence and deletes that key from `cache`, even though a newer entry for the same
index is still sitting in `cacheOrder`. The result: `cacheOrder.count` stays at 48
while `cache.count` drifts below it. The cache is not a leak, but it holds fewer
than 48 frames — sometimes far fewer.

This is not merely wasteful; it is a **multiplier on C2**. A smaller effective cache
means the ping-pong turn falls out of cache sooner and the per-frame reader restarts
begin earlier.

There is a second-order effect: a just-stored frame can be evicted by its own stale
duplicate on the very next `store`, so a frame can be decoded, cached, and dropped
before it is ever read back.

**When it bites.** Any backward travel or stepped playback — so, ping-pong and the
shuttle's step buttons. Within minutes of using either.

**Suggested fix.** Dedupe on store: `if cache[index] == nil { cacheOrder.append(index) }`
before assigning, or move the index to the back of the order when it is already
present. An `OrderedSet`-style structure, or just `cacheOrder.removeAll { $0 == index }`
before the append (48 elements, so the linear scan is free) is enough.

## C14 — `FrameRecorder.write` adds a third per-pixel swizzle loop per feed per frame

**Medium.** `App/.../Platform/FrameRecorder.swift:224-238`.

```swift
image.pixels.withUnsafeBufferPointer { source in
    for y in 0..<height {
        for x in 0..<width {
            destination[to]     = source[from + 2]   // RGBA in, BGRA out
            destination[to + 1] = source[from + 1]
            destination[to + 2] = source[from]
            destination[to + 3] = source[from + 3]
        }
    }
}
```

345,600 iterations per feed per frame, on the render thread, converting RGBA back to
BGRA. Chase the provenance: the GPU texture is `.bgra8Unorm` → `readback`'s staging
texture is BGRA → `ImageBuffer.fromBGRA` swizzles it to RGBA → this loop swizzles it
back to BGRA for the pixel buffer. **Two full-frame scalar passes to produce bytes
identical to what `staging.getBytes` already wrote.**

With all seven feeds armed that is seven readbacks (C3) plus fourteen full-frame
scalar passes per frame.

**When it bites.** The moment recording starts, and it is a recording session that
runs for hours by definition.

**Suggested fix.** Falls out of C3 and C12: add a BGRA-native readback path that
writes `staging.getBytes` output directly into the pooled `CVPixelBuffer`'s base
address, respecting `CVPixelBufferGetBytesPerRow`. That removes both passes and one
of the two allocations. Note the pixel buffer's stride may not equal `width * 4`, so
it has to stay a per-row `memcpy` rather than one flat copy — still two orders of
magnitude cheaper than the scalar loop.

## C15 — Eight `nextDrawable()` calls per frame on the main thread

**Medium.** `App/.../Render/MetalPreviewView.swift:441-470` (`:451`) and `:473-487`
(`:474`); driven from `App/.../UI/ShellController.swift:2231-2260`.

`refresh(from:)` calls `present()` on four source previews, two sub-mix previews and
the programme preview, then `outputWindow?.present(...)` — eight `CAMetalLayer`s,
each calling `nextDrawable()`, all on the main thread, all inside `tick`.

`nextDrawable()` blocks when every drawable in that layer's pool is still in flight.
The layers are created at `:98-106` with no `maximumDrawableCount` set (default 3)
and `allowsNextDrawableTimeout` left at its default `true` — so a blocked call
returns `nil` after approximately **one second**. One second is thirty dropped
frames.

Nothing here waits on completion, and everything shares the single
`MetalContext.commandQueue` (`MetalContext.swift:779`), which is what keeps the
preview blit correctly ordered against the node that will overwrite the same texture
next frame — that part is sound and worth not disturbing. The exposure is purely the
blocking acquire.

Secondary: `present()` is called unconditionally for every preview, including ones
in a collapsed rail or a hidden panel, so hidden previews consume drawables too.

**When it bites.** Under exactly the conditions the other findings create — once a
frame runs long, drawables stay in flight, and the next frame's acquire blocks. It is
an amplifier: it turns one slow frame into a visible freeze.

**Suggested fix.** Set `allowsNextDrawableTimeout = false` and
`maximumDrawableCount = 2` on each layer at creation, and skip `present()` for any
preview whose view is hidden or has zero area. Better still, acquire the drawable
*after* checking `texture != nil` and bail early when the view is off-screen — the
current code calls `nextDrawable` even on the clear path (`:474`).

## C16 — `applyAllParameters()` runs twice per frame

**Low.** `App/.../Render/Engine.swift:551` and `:613`.

`tick` calls it at `:551`; `evaluate` → `evaluateGraph` calls it again at `:613`. The
second call is pure waste: nothing writes to the registry between them.
`applyAllParameters` (`:569-604`) walks roughly 35 nodes, each doing several
`ParamRegistry.value` lookups — two dictionary hashes apiece
(`ParamRegistry.swift:139-141`) — so a few hundred redundant lookups per frame.

The duplication exists because `evaluateGraph` is shared with the self-QA checks,
which call it without a preceding `tick`. That is a real constraint, not an oversight.

**Suggested fix.** Give `evaluateGraph` an `applyingParameters: Bool = true`
parameter and pass `false` from `tick`, or split out an
`evaluateGraphWithoutApplying` that `tick` calls after its own
`applyAllParameters()`. Keep the self-QA entry point as it is.

## C17 — Evaluation order and edge lookups are re-derived with fresh allocations every frame

**Low.** `Core/.../Graph/RenderGraph.swift:71-76`, `:82-106`; used at
`Engine.swift:618-620`.

```swift
for identifier in graph.evaluationOrder(from: Engine.outputSlot) {   // :618
    let inputs = graph.inputs(of: identifier).compactMap { produced[$0] }  // :620
}
```

`evaluationOrder` builds a fresh `[String]`, two `Set<String>`s and a recursive
closure every frame. `inputs(of:)` runs `filter` + `sorted` + `map` over the entire
edge list — three allocations — *once per node*, so the whole thing is
`O(nodes × edges)` with an allocation per step. With ~35 nodes and ~40 edges, and
`String` keys (hashing and reference counting on every compare), this is a few
hundred small allocations per frame.

Not currently a frame-rate risk. It is listed because it is the piece that scales
badly if the node count ever grows, and because it is trivially cacheable: the graph
only changes on an explicit `add`/`connect`.

**Suggested fix.** Cache `evaluationOrder` and a `[String: [String]]` inputs map on
`RenderGraph`, invalidated by a version counter bumped in `add` and `connect`. The
render loop then iterates a prebuilt array. This also makes the mid-render
reconfiguration question (S1) tractable, because there is then one place where the
graph's shape is snapshotted.

## C18 — Nothing tears down the engine; the display link retains it

**Low.** `App/.../Render/Engine.swift:514-528`; `App/.../Output/OutputRouter.swift:352`.

`Engine.stop()` has no production caller. (`AudioInput.swift:114` has
`engine.stop()`, but that `engine` is the local `AVAudioEngine` — a name collision,
not a call.) `OutputRouter.closeAll()` is called only from
`App/.../Platform/StreamSelfQA.swift:124`. `AppDelegate` implements
`applicationShouldTerminate` (`:153-182`) but no `applicationWillTerminate`, so
neither runs at quit.

`start(drivenBy:)` creates the link with `view.displayLink(target: self, ...)` and
adds it to the main run loop (`:516-518`). `CADisplayLink` retains its target, and
the run loop retains the link, so the `Engine` — and transitively the whole graph,
every cached texture, the registry and the MIDI client — is retained for the process
lifetime. Given the app is single-window and quits with its window
(`AppDelegate.swift:185`), this is not a growing leak.

The real consequence is at shutdown: `MPEGTSStreamer.close()` (`:218`) writes the
trailer and flushes the encoder, and it is reached only via `deinit` (`:159`) or
`closeAll()`. Process exit runs neither. **Every stream ends truncated**, and any
in-flight `AVAssetWriter` recording is likewise never finished.

**Suggested fix.** Add `applicationWillTerminate` to `AppDelegate` calling
`engine.stop()`, `router.closeAll()`, and `recording?.finish { }` — the last needs
`.terminateLater` handling since `finishWriting` is asynchronous, which
`applicationShouldTerminate` already has the shape for. Making the guard at `:515`
symmetric (`stop()` clears `displayLink`, which it does) means `start`/`stop` can be
called in pairs safely.

# SUSPECTED

These follow from reading the source and are consistent with it, but each depends on
a runtime ordering or a usage pattern I could not confirm without running the app.

## S1 — Graph reconfiguration is safe only by main-thread coincidence, and nothing documents that

`RenderGraph.add` (`:46-51`) and `connect` (`:55-68`) are called at runtime from
`setChannelSource` (`Engine.swift:740`) and `setProgramShowsTestPattern` (`:927`,
`:936-941`), both from UI actions. `tick` also runs on main (`:516-517`, `.main`
run loop), so a reconfiguration cannot interleave with an evaluation — today.

Two things make that fragile rather than fine:

- `fireActionTriggers` (`ShellController.swift:1639-1640`) and
  `flipAutomatedButtons` (`:1669`, `button.target?.perform(...)`) invoke arbitrary
  UI action handlers **from inside `refresh(from:)`, i.e. from inside `tick`**. Those
  handlers can reach `setChannelSource` or `removeEffect`
  (`ShellController.swift:1561`). So a graph mutation can occur partway through a
  frame's UI update, after `evaluateGraph` has already produced
  `currentTextures` against the old shape. Frames straddling the change render
  against a half-updated graph.
- Nothing in `RenderGraph` asserts main-thread-only, and the type is a plain
  `final class` with no isolation. The first background decode or capture callback
  that calls `connect` will corrupt `edges` silently.

**Why suspected:** I could not confirm that any reachable action handler actually
mutates the graph during a tick — it depends on which buttons are automatable.

**Suggested fix.** Mark `RenderGraph` `@MainActor`, or add a
`dispatchPrecondition(condition: .onQueue(.main))` to `add`/`connect`. Separately,
defer the action-trigger and automated-button dispatch to the end of `tick` (or to
the next run-loop turn) so a handler cannot mutate the graph mid-frame.

## S2 — A feedback send from an *upstream* slot has no one-frame delay

`applyFeedbackSends` (`Engine.swift:861-864`) sets `feedback.externalHistory` from
`currentTextures[slot]`, and the comment at `:855-860` argues this is safe because
it is the previous frame's texture.

That holds when the send source sits **downstream** of the feedback node — bus ONE's
chain is `subMixOne → … → feedback → mx1One → busCodecOne`, so `mx1One`'s cached
target has not yet been rewritten when `feedback` renders.

It does not hold for an upstream source. Sending `mix.one` into bus ONE's loop points
`externalHistory` at `CrossfadeNode`'s reused target
(`Core/.../Modules/Mix/CrossfadeNode.swift:79`), which `evaluateGraph` overwrites
*earlier in the same frame*. The loop then reads the current frame, not the previous
one — a zero-delay path that the graph's cycle detection cannot see, because it is
not an edge.

**Why suspected:** the visible result (a harder, more immediate feedback than
intended) is a judgement call, not obviously a bug, and it depends on which sends the
UI actually offers. Worth confirming against `RoutingPopover`'s source list.

**Suggested fix.** If the guarantee is meant to hold, copy the texture when the send
source is upstream of the target bus — `MX1EffectNode.copy` (`:100-111`) is the
existing pattern. Cheaper: restrict feedback-send sources to slots downstream of the
loop and grey out the rest, which makes the invariant structural.

## S3 — `ObjectKey` can alias a deallocated control

`ShellController.swift:2333-2343`. `ObjectKey` hashes on an `ObjectIdentifier`
captured at init while holding the button only weakly. Once the button deallocates,
the identifier is a stale address that a newly allocated object can reuse — so a
lookup in `automatedButtons` (`:1674`) could hit a stale entry belonging to a
different control.

Entries are only cleared by a wholesale rebuild in `refreshAutomatedButtons`
(`:1677-1688`), so between rebuilds the map holds keys for dead objects. The
`guard let button = key.button` at `:1662` stops them being *used*, which is why
this is suspected rather than confirmed — the weak check almost certainly catches it
first. But "almost certainly" is the whole basis, and the panels do get rebuilt
(`EffectChainPanelBody.rebuild()` at `:246`).

**Suggested fix.** Prune on rebuild (already done) *and* drop entries whose
`button` has gone nil at the top of `flipAutomatedButtons`, so a stale identifier
never survives to be compared against a fresh one.

## S4 — `armedSweeps` holds strong references to faders

`ShellController.swift:1714`: `[(fader: VBFader?, write: (Double) -> Void)]`. The
`fader` is a strong optional, not `weak` — the tuple label reads like the weak
pattern used next to it but is not. The `write` closures do capture `[weak panel]`
and `[weak body]` (`:1729`, `:1744`), so the intent is clearly weak throughout.

Faders removed from the view hierarchy stay alive until the next
`refreshArmedSweeps()`. That is bounded and small; it is listed because the
adjacent `ObjectKey` type went to real trouble to be weak, so this looks like an
oversight rather than a decision.

**Suggested fix.** `weak var` inside a small struct, or store `ObjectKey`-style
handles.

## S5 — `beatSubdivision` is not connected to anything that schedules

`Engine.swift:824-829` defines `beatSubdivision` with a `didSet` that logs, and its
own doc comment says a previous version "changed a label and nothing else". The
current version still changes only a label and a log line: `buildSchedule`
(`:493`, `:504`) hardcodes `.quarter` for all seven subscriptions, and no other
code reads `beatSubdivision`.

**Why suspected:** it may be intentionally inert pending a later phase. Flagging it
because C7's four-hour arithmetic changes by 4× the moment it is wired up, so the
fix for C7 should land first.

# Corrections to the leads

Things in the brief that turned out to be wrong or overstated:

1. **`setProgramShowsTestPattern` does restore the mix routing.** Lines `:940-941`
   reconnect `mx1One → busCodecOne → primary[0]`, and `busCodecTwo`/`busCodecProgram`
   never lost their edges (`RenderGraph.connect` keys on identifier strings, which are
   unchanged). The topology is intact. The genuine damage is the un-restored
   crossfader, the orphaned scheduler subscriptions, and the lost `interchange`
   state. See C4.

2. **Parameters *are* effectively re-registered** in that path — not by
   `registerParameters`, but because the slot names are unchanged and
   `applyAllParameters` pushes registry values into whatever object
   `Engine.busCodecOne` now points at. The lead listed "parameters never
   re-registered" as a defect; it is a latent fragility, not a live one.

3. **Scheduler growth at 1/16 is not currently reachable.** All seven subscriptions
   are hardcoded to `.quarter` (`Engine.swift:493`, `:504`); `beatSubdivision` is
   inert (S5). The real four-hour figure is ~200 k events / ~6.5 MB, not the ~800 k
   the 1/16 framing implies. Still worth fixing, and worth fixing *before* the
   subdivision is wired up.

4. **Timers and observers are clean.** The brief asked about retain cycles from
   timers and observers. There are **zero** `NotificationCenter`, `addObserver` or
   KVO registrations in either target. All four repeating `Timer`s
   (`RecordButton.swift:115`, `VBFader.swift:152`, `ShellView.swift:112`,
   `EmuScreenView.swift:93`) use `[weak self]`, invalidate in `deinit`, and either
   self-terminate or are stopped by an explicit `stop`. This is not a leak vector;
   the leak vector is the scheduler closure in C4.

5. **`CaptureSourceNode` is correct** and was worth checking. `submit(frame:)`
   (`:75-81`) is properly locked, keeps only the newest frame, and `render`
   (`:90-103`) takes the pending frame under the same lock. Last-frame-wins with no
   queueing is exactly right for a capture source. No finding.

6. **The `waitUntilCompleted` count is higher than the note in `CLAUDE.md`
   implies**, though the conclusion there still stands. A full tick with everything
   active runs roughly 10–14 blocking GPU round trips (one per active effect node,
   plus one per `blend`, plus one per `readback`). `CLAUDE.md` already records this
   as the known structural risk and says not to refactor it while it measures fine —
   I agree, with one amendment: **C1 and C3 make the count unbounded**, because a
   ring rebuild adds 62 and each readback adds one. Fix those two and the hard-sync
   count goes back to being bounded and fine.

7. **A note on the Explore survey, not the brief:** the survey attributed the
   bus-codec reconstruction to `setInterchange(_:forBus:)` at `Engine.swift:810`.
   That function only assigns a property (`:812-814`); the reconstruction is in
   `setProgramShowsTestPattern` (`:933-938`).

# Suggested order of work

Ranked by frames-saved-per-line-changed, not by severity:

1. **C4** — delete twelve lines of copy-paste, restore one registry value. Smallest
   change on the list, removes a permanent leak and a dead crossfader.
2. **C1** — allocate the feedback ring once at maximum size. One `if`. Removes the
   single worst frame the app can produce.
3. **C13** — dedupe `cacheOrder`. Three lines, and it is a prerequisite for C2
   being worth doing.
4. **C5** — move the stderr write off the caller's thread, rate-limit
   `ClipSourceNode:553`. Removes an unbounded stall.
5. **C3** — cache the staging texture and byte buffer in `OffscreenRenderer`. One
   change, benefits recording, streaming and every bus codec at once.
6. **C2** — the reader restart. Largest piece of work here; do it after C13 so the
   cache is actually 48 frames deep.
7. **C6, C8/C9, C10/C11** — the thread-boundary set. Independent of each other and
   of the above.
8. **C12/C14** — the swizzle chain. Best done as one change (a BGRA-native
   `ImageBuffer` path), and ideally alongside introducing a `CVMetalTextureCache`.

C15 through C18 and the `SUSPECTED` items are worth a pass once the above are in;
none of them will drop a frame on their own.
