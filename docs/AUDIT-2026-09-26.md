# Audit — soak, real footage, controls, loose ends (2026-09-26)

Branch `perf/audit`. Follows `AUDIT-2026-09-23.md` (P1–P7 fixed there).

Method: measured on a **release** build, real window, live display link. Four checks
added this session:

- `selfqa soak`: `stress`'s full load (4 channels, every effect, six datamoshes) held for
  minutes while doing what a performer does every 2 s (drop a clip, cut, fade, flip an
  effect, eject + reload, swap A/B, a scope key). It samples memory, GPU allocation,
  threads and file descriptors every 30 s, and blames each tick over 14 ms on its
  costliest part. It takes `VIDEOBOY_SOAK_MINUTES` and `VIDEOBOY_SOAK_CLIPS` (four paths).
- `selfqa decode`: per-file cost on the main thread (open, first frame, steady, worst,
  memory held, cold thumbnail). Add real footage with `VIDEOBOY_BENCH_CLIPS`.
- `selfqa audit`: now moves every enabled fader through its own action and asserts the
  engine's value at the fader's mapping address changes.
- `leaks --atExit` around a soak.

Evidence: `selfqa/out/perf/{soak,soak-20min,soak-hd,decode,leaks,dead-code}/`.

## Headline

**The app is solid on the SD fixtures and not ready for real footage.** Every
"30 fps, 0 dropped" number so far, this one included, came from `samples/`: four
small synthetic SD files. Camera and phone footage costs 5–20× more to decode, and all
decoding happens on the main thread, inside the render tick.

| Soak | Frames | Dropped | Tick mean | Ticks > 16 ms | Worst | Memory |
|---|---|---|---|---|---|---|
| 20 min, SD fixtures | 35,964 @ 29.97 | **1** | 8.9 → 9.3 ms | 186 | **62 ms** | flat, +0.45 MB/min |
| 3 min, 2× 1080p H.264 + ProRes + DV | 5,391 @ 29.95 | **7** | **21–30 ms** | **every tick** | **75 ms** | peak **1.76 GB** |

**Leaks: 0.** `leaks --atExit` after a 2-minute soak with about 20 clip swaps and
eject/reloads found 0 leaks in 560,056 live allocations. Over 20 minutes GPU
allocation, thread count and file descriptors stayed flat. Timers, notification
observers and stored callbacks were read by hand, and all of them use weak captures
and are torn down.

### Per-file decode cost, main thread (`selfqa decode`)

| Clip | Open | 1st frame | Steady/frame | Worst | Held | Cold thumbnail |
|---|---|---|---|---|---|---|
| bars.dv / motion.dv (SD) | 6–8 ms | 2–5 ms | 1.2–1.4 ms | 2.4 ms | ~25 MB | 4–5 ms |
| motion.m2v (SD) | 11 ms | 2 ms | 0.7 ms | 1.2 ms | 29 MB | **141 ms** |
| motion.mov (SD) | 19 ms | **61 ms** | 1.4 ms | **47 ms** | 46 MB | 11 ms |
| 1080p H.264, 2 s GOP | 5 ms | 25 ms | **6.3 ms** | 9.6 ms | **311 MB** | 33 ms |
| 1080p ProRes 422 | 13 ms | 15 ms | **6.1 ms** | 11 ms | **379 MB** | 24 ms |
| 4K HEVC | 12 ms | 90 ms | **26 ms** | 42 ms | **1.1 GB** | 89 ms |

"Held" is the footprint difference across the load, so it's approximate: it depends on
what earlier clips freed, and a rerun read 4K at 91 MB. The decode times repeat within
~10%. The soak's peak memory (1.7 GB with HD) is the reliable memory figure.

Four HD channels spend about 25 ms of the 33.4 ms frame on decode alone. One 4K
channel spends nearly all of it.

## Findings

Status: **OPEN** (in the plan below) · **FIXED** (this session)

### Frame path: stutter

| # | Finding | Evidence |
|---|---|---|
| F1 | **Every source decodes synchronously in the render tick** (`ClipSourceNode.render` → `clipDecoder.image(at:)`). This is P5 from the last audit, and real footage makes it the dominant cost. | Soak spike attribution: every tick over 26 ms was a `source.*` node (40–54 ms), none was an effect. |
| F2 | **AVFoundation clips decode at native resolution.** A 1080p frame is 8.3 MB, and the 48-frame cache holds ~400 MB per channel. 4K holds 1.1 GB. The GPU upload is full size too (GPU 412 MB in the HD soak vs 138 MB SD). | `AVFClipDecoder.restartReader`: output settings carry a pixel format but no width/height. |
| F3 | **BGRA→RGBA per-pixel Swift loop** in `AVFClipDecoder.imageBuffer(from:)`, on the main thread. Then `TextureUploader` swizzles it back, so every frame is converted twice. CLAUDE.md forbids CPU pixel loops on the frame path. | `AVFClipDecoder.swift:217–229` |
| F4 | **An AVFoundation reader restart costs 47–90 ms.** It happens on the first frame after a load or swap, and at every loop wrap. That's the source of the soak's 20–26 ms periodic spikes and the 62–68 ms stalls. | decode bench, motion.mov worst 47 ms; soak attribution. |
| F5 | **Every decoded frame allocates and zero-fills a new 1.38 MB pixel array** (DV, MPEG and AVF), plus a 120 KB corrupted-bytes copy and a 120 KB libav packet (DV). That's ~180 MB/s of allocator churn at 4 × 30 fps, on the main thread. `TextureUploader` fixed the GPU side of this and the CPU side remains. | `DVDecoder.swift:179`, `MPEGStreamDecoder.swift:278`, `AVFClipDecoder.swift:217` |
| F6 | **The three scopes refresh in the same tick.** Every ~5th frame does up to three GPU readbacks plus CPU composes. That caused the 70 `ui/onFrame` spikes, and p95 rises from 8.7 to 14.6 ms with data burn on. | soak attribution; `ShellController.updateScopes` |
| F7 | **Streaming does its readback, swscale, MPEG-2 encode *and network write* on the main thread**, every frame, plus a 1.38 MB copy (`var pixels = image.pixels`). CLAUDE.md: "no synchronous file or network I/O, ever". | `OutputRouter.present` → `MPEGTSStreamer.send` |
| F8 | **Recording does one synchronous GPU readback per armed feed per frame**, up to 7. Neither `stress` nor `soak` measures a show with recording or streaming running. | `RecordingSession.write` |
| F9 | A clip load or eject + reload blocks the main thread for 10–26 ms (open, probe, first decode). With the ~9 ms tick that's ~31–35 ms, right at the frame budget. | soak `actions.csv` |

### Controls: accounted for

`selfqa audit`: **1,259 controls. 747 live, 512 disabled, 0 enabled-but-unwired.** Of
the 512 disabled, 480 are plain labels, 9 are scrollers, and ~23 are real buttons that
are disabled until their state allows them (scope options until a scope is on, emulator
keys until a machine runs). The rest are the Save keys (L1) and the header buttons (L9).

**Faders, by behaviour rather than wiring:** 99 enabled, all Shift-learnable. 93 change
the engine when moved and 6 don't (L3). Buttons, pop-ups and segmented controls are
still checked for wiring only (see H3).

## Game plan — leaner, meaner

Ordered by what a performer feels. Each step lands behind a switch with the old path
as fallback (the way `VIDEOBOY_SYNC_EVERY_PASS` did), is measured with `soak` on
**real footage** before and after, and is committed separately.

### 1. Get decoding out of the tick (F1–F5, F9) — the big one
1. **Decode at SD, in hardware.** Give `AVAssetReaderTrackOutput` a 720×480 size and let
   VideoToolbox scale. HD per-frame memory 8.3 → 1.4 MB, cache 311 MB → ~66 MB, and the
   GPU upload is 6× smaller. Small, contained, the biggest single win. *~2 h.*
2. **Zero-copy AVFoundation frames.** IOSurface-backed `CVPixelBuffer` →
   `CVMetalTextureCache` → `MTLTexture`. Deletes the per-pixel loop (F3) and the second
   swizzle, and there's nothing left to allocate per frame. *~3 h.*
3. **A per-source background decoder with a prefetch ring** (P5). A serial queue per
   channel decodes ahead of the playhead into N reused buffers. `render` takes the ready
   frame, or holds the previous one and counts a miss. The playhead still advances on
   the tick, so the frame-clocked invariant holds. The loop start stays pre-decoded, so
   wraps and swaps stop restarting the reader (F4). DV/MPEG decode into reused buffers
   (F5). *~1–2 days; concurrency on the frame path, so it gets its own review.*
4. **Open clips off the main thread** (F9): probe and first frame in the background,
   swapped in when ready, so the old clip keeps playing until then. *~3 h after 3.*

Target, measured by `soak` with 4 HD channels: tick mean < 10 ms, 0 ticks over one
SD frame, 0 dropped, peak memory < 800 MB.

### 2. Take the rest of the main thread back (F6–F8, R1–R3)
5. **Stagger the scopes**: one per tick, compose off-main. *~1 h.*
6. **Async readback for record and stream**: blit to a shared buffer, completion
   handler. Encode and network write on a serial queue, never the main thread. *~4 h.*
7. **Thumbnails off-main**: a placeholder, then the picture. One decoder per clip serves
   all 12 hover steps, the cache gets an LRU cap (~64 MB), and m2v uses the MPEG decoder
   (141 ms → ~10 ms). *~4 h.*
8. **Batch library duration results** into one rebuild. *~30 min.*

### 3. Close the loose ends (L1–L9)
9. **Patch save/load** (L1): wire `TemplateDocument` to File ▸ Save/Open, the quit
   prompt and the FX Save keys. This is the largest *functional* gap. *~1 day.*
10. **Apply the calibrated feedback latency** (L2) and persist it in preferences. *~1 h.*
11. **Route the emulator faders through the registry** (L3). *~1 h + hands-on check with
    the Amiga running.*
12. **Decide on the native titler** (L4): wire it (fix readback and allocation first) or delete ~700 lines.
13. **Delete the 22 dead declarations** (L6), demote the per-beat log lines to debug (L7),
    fix the ISF collision (L5: namespace by folder, or show it in the Add menu), label
    the header buttons (L9), bring TODO.md and CLAUDE.md up to date (L8). *~2 h together.*

### 4. Keep the harness honest (so this can't hide again)
- **H1** Generate real-footage fixtures in `make-fixtures.sh` (1080p H.264, ProRes, 4K
  HEVC, all synthetic via ffmpeg, no copyrighted media) and put **at least one HD
  channel into `stress`**. A green stress on SD-only fixtures is what hid F1–F4.
- **H2** A 3-minute HD `soak` as the pre-show check; the 20-minute run as an overnight check.
- **H3** Extend the audit's fader actuation to pop-ups, segmented controls and toggle
  keys (modal-opening buttons excluded by identifier).
- **H4** A `stress` phase with recording on every feed and a stream running.
- **H5** `verify.sh` is **red on a pre-existing flake**:
  `DatamoshNodeTests.testTheNodeMoshesACutLiveWithoutEverWaitingOnTheTick` asserts a
  wall-clock worst render under 8 ms inside `swift test`, a **debug** build. It failed 2
  of 3 isolated runs (12 ms), and an earlier `node-timing.txt` shows 13 ms. Nothing in
  `Core/` changed this session. Assert "never waits" structurally (median, or a count
  of fence waits), and leave worst-case timing to the release-build `stress`/`soak`.
