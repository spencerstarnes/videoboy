## New findings (not in AUDIT-2026-09-26.md)

### S1 — The catalog's launch cost is invisible to the one screen built to show launch cost

**FIXED (2026-09-27, step 1):** `LaunchStage.library` ("Library catalog") is reported around `openCatalog`; a catalog that will not open now skips the stage with a status-strip notice instead of a launch-time modal. Moving `backUpIfDue`'s `VACUUM INTO` off the launch path stays a backlog item.


`LaunchWindowController.swift` exists specifically so no part of startup reads as a
hang: its own header says "showing what is happening turns that pause into
information rather than a hang," and its `Extend` note is explicit — "add a
`LaunchStage` case and report it at the right moment." Its `LaunchStage` enum has
eight cases: metal, shaders, codecs, graph, clock, midi, displays, interface.
**There is no catalog/library stage.**

`AppDelegate.applicationDidFinishLaunching` (`AppDelegate.swift:56–58`) calls
`openCatalog(into:)` between `codecs` completing and `graph` completing. That call
chain is synchronous and unbounded by design:

- `Catalog.init` (`Catalog.swift:108–138`) does `flock`, `sqlite3_open_v2`, a
  migration, and — once a week — `backUpIfDue`'s `VACUUM INTO`, which does a full
  page-by-page copy of the whole catalog file (`Catalog.swift:316–347`).
- `LibraryModel.attach` (`LibraryModel.swift:252–276`) then does a synchronous
  `catalog.loadClips()` — `SELECT … ORDER BY position` over every row, allocating a
  `CatalogClip` per row — still on the main thread, still before `graph` lights up.

Both costs scale with library size, and neither is capped. For the 1,000-clip
library the 0.4.7 import test built, this is probably fast enough to be invisible in
the good sense. But the catalog is meant to accumulate for years (that's the entire
point of 0.4.7 — "the library a performer builds is the library they come back
to"), and unlike every other stage in this window, nothing here gets slower and then
tells you why. On the one day a week the backup fires *and* the library is large,
launch will pause between "DV codec" and "Render graph" with every dot still grey —
structurally indistinguishable from the hang this screen was built to rule out.

**Fix shape:** add `case library = "Library catalog"` to `LaunchStage`, report it
around the `openCatalog` call, and — separately worth a backlog line — move
`backUpIfDue`'s `VACUUM INTO` off the launch path entirely (it doesn't need to block
opening the catalog for writing; it could run after `graph`/`interface` complete, or
on a background queue with the UI already up).

**Severity:** low today, grows with every library import. Not in AUDIT-2026-09-26.md
(L1–L10 don't mention the catalog's launch path; the audit's own R1–R3 UI-cost
findings are about the library browser, not startup).

### Concurrency review of the frame path (the one thing AUDIT-2026-09-26.md admitted it skipped)

The audit's own game plan, item 3, flags "a per-source background decoder with a
prefetch ring... concurrency on the frame path, so it gets its own review" and then
never does it. Ran that review (`ClipPrefetcher`, `AVFClipDecoder`, `ClipDecoders`,
`DVDecoder`, `MPEGStreamDecoder`, `ClipSourceNode`, `Engine`, `TextureUploader`, read
in full, not excerpted).

**Headline: the prefetcher itself is clean.** `ready`/`wanted`/`urgent`/`pumping` are
all read-modify-written under one `NSLock` acquisition each (no check-then-act
splits), every recursive `queue.async` captures `[weak self]` so an ejected clip's
pump chain self-terminates, `ImageBuffer` is a value type so frames crossing the
decode-queue/main-thread boundary can't be mutated from under a reader, and a
swapped clip gets a wholly separate `ClipPrefetcher` object rather than mutated
shared state — so there's no stale-completion class of bug to find because there's
no shared mutable state for a stale completion to land in. No data races, no
deadlocks, no retain cycles found in the hot path.

Three smaller things, none of them frame-path stutter risks:

### S2 — `av_log_set_level` is an unguarded write to libav's global log level

`MPEGStreamDecoder.swift:115` calls `av_log_set_level(AV_LOG_QUIET)` inside
`init()`, which runs on whichever thread opens a clip — a channel's own decode
queue, *or* `ClipDecoders.duration(of:)` called from the background `ImportJob`
while scanning a folder of `.m2v`/`.mpg` files (CLAUDE.md: imports run off the main
thread). Two clips opening concurrently — an import batch scanning MPEG files while
a live channel loads one — write this process-global from different threads with no
synchronization. **Failure scenario:** worst case is a transiently wrong log level
(FFmpeg chatter briefly reappears in the log, or vice versa); it's C global state
with no memory-safety consequence, not a crash. Fix: call it once at process start
(a `static let` token), not per-decoder-init.

### S3 — `ClipPrefetcher.image(at:damage:)` has a latent reentrancy deadlock

`ClipPrefetcher.swift:100`'s unbounded-wait entry point (used by `renderToImage` and
self-QA) does `queue.sync { decoder.image(...) }`. Safe today — nothing that runs
*on* `queue` currently calls back into this method on the same prefetcher. But
GCD's serial-queue reentrant `sync` hangs forever, and there's no guard against it:
a future decoder that lazily opens a second clip and asks its own prefetcher for a
frame mid-decode, or a self-QA helper invoked from a callback already queued on
`queue`, would deadlock the process permanently. **Failure scenario is entirely
hypothetical today** — flagging it because it's a landmine for the *next* person to
touch this file, not a live bug. Fix: a comment stating the invariant, plus
`dispatchPrecondition(condition: .notOnQueue(queue))` in debug builds.

### S4 — Core is Swift 6 tools, Swift 5 language mode, on purely manual concurrency

`Core/Package.swift` declares `swift-tools-version: 6.0` but every target opts into
`.swiftLanguageMode(.v5)` (lines 47, 53, 59). Combined with `ClipPrefetcher` using
raw `DispatchQueue`/`NSLock`/`DispatchSemaphore` with zero `Sendable`/actor
annotations, none of the correctness described above is compiler-enforced — it's
correct because this review (and whoever wrote it) reasoned carefully about it, not
because the compiler would catch a regression. Not a bug; a note that if S2/S3-class
issues are worth closing structurally rather than by convention, `ClipPrefetcher`
would need real Swift 6 concurrency checking (`@unchecked Sendable` at minimum, with
the file's own `THREADING` comment turned into an enforced contract).

**None of S2–S4 change the "safe today" verdict on the frame path.** Given how
carefully AUDIT-2026-09-26.md's F1–F9 already dissects this exact code for
performance, this — a mostly clean concurrency bill of health — is itself the
useful new information: the audit's open "needs its own review" item can be closed
as reviewed, with S2/S3 as small, non-urgent follow-ups.

### S5 — Waking from sleep replays every missed beat in one render tick (proven, not just read)

**FIXED (2026-09-27, step 1):** `Scheduler.advance` skips boundaries older than `maximumCatchUpBeats` (2 beats) instead of replaying them, and logs how many beats it skipped per subscription (the dead `nowBeats - horizonBeats` warning is gone). Regression: `ClockTests.testAnEightHourGapInOneAdvanceFiresABoundedNumberOfEvents` — ≤ 12 fires across an 8-hour gap, then normal sixteenths.


`Scheduler.advance(to:)` (`Core/Sources/VideoboyCore/Clock/Scheduler.swift:121–175`)
is called once per render tick from `Engine`'s display-link callback
(`Engine.swift:941`) — the exact frame path CLAUDE.md says must never stutter.

For each subscription, the per-boundary loop (`Scheduler.swift:132–155`) walks from
`subscription.lastScheduledBeat` up to `horizonBeats` (≈ now + 0.2 s), firing every
boundary it passes through **synchronously, in this one call**. Nothing caps how far
behind `lastScheduledBeat` can be. The comment directly above the trailing check
claims otherwise — *"A very late advance (the app was suspended) would otherwise
replay every missed boundary at once... the per-subscription cursor has already been
moved past them"* — but the code doesn't do what the comment describes: there is no
skip-ahead, only the same fire-every-boundary loop that runs on every ordinary tick.

**Proved it, rather than just reading it.** Added a temporary test (not committed —
reverted after confirming, since a permanently-failing test would break
`verify.sh`): `Transport` at 120 BPM, one subscriber, `advance(to: 0)` then
`advance(to: 8 * 3600)` — one call, simulating a single display-link tick right
after the Mac wakes from an 8-hour sleep. **Result: 57,600 events fired
synchronously inside that one call** (exactly 2/s × 28,800 s, as the math predicts).
Every one of Engine's beat subscriptions (source reseed ×4, bus data-effect reseed
×3 — see the per-beat log lines just removed in `cleanup-dead-code.md`) would do
this at once on wake, each invoking its reseed closure in a tight loop.

**The self-diagnostic for this exact scenario is also dead code.** The warning at
`Scheduler.swift:172–174` — `if nowBeats - horizonBeats > 1 { Log.warn(...) }` — can
never fire: `horizonBeats` is *always* greater than `nowBeats` by construction
(`horizonBeats = transport.beats(atHostTime: hostTime + lookaheadSeconds)`, and
`lookaheadSeconds` defaults to +0.2 s), so `nowBeats - horizonBeats` is always
negative. The comment's own claim ("some beats were skipped") doesn't match what the
code does (replays, doesn't skip) — this check looks like it was meant to compare
`nowBeats` against the *pre-loop* `lastScheduledBeat`, not against `horizonBeats`.
So even the belt-and-suspenders logging for this case is silently broken; nobody
would see a warning about it in the field.

**Failure scenario, concretely:** a performer closes their MacBook's lid mid-show
(sleep) with the transport running, or the Mac goes to sleep after being idle at a
break. On wake, the first display-link tick calls `advance()` with a multi-hour gap.
That tick executes 10,000+ closures (array append + a reseed call each) before it
can render or present a frame — a stall of unknown but almost certainly
multi-hundred-millisecond-to-multi-second duration, landing exactly at the moment a
performer resumes a show. This is the same class of problem as the CLAUDE.md
"smooth playback outranks everything" rule was written for, just triggered by clock
math rather than decode cost — and it's a plausible thing to hit while testing on a
laptop that sleeps, which the SD-fixture-only `stress`/`soak` checks (both driven by
smoothly incrementing host time) would never exercise.

**Not in AUDIT-2026-09-26.md** — none of F1–F9 (decode/GPU cost) or L1–L10
(functional gaps) touch the scheduler's catch-up behavior; H5 is the only clock-
adjacent item and it's about a flaky *test's* timing threshold, unrelated.

**Fix shape** (not attempted — this is a report, not a patch): in the per-subscription
loop, if `nextBoundary(after: lastScheduledBeat, ...)` is more than, say, a few beats
behind `nowBeats`, snap `lastScheduledBeat` forward to just behind `horizonBeats`
before walking (skip instead of replay) and log once per subscription with how many
beats were dropped. Separately fix the dead warning condition to compare against the
pre-loop position, not against `horizonBeats`.

### S6 — A clip that fails to load freezes the whole app on a modal alert (HIGHEST SEVERITY)

**FIXED (2026-09-27, step 1):** `ShellController.presentNotice` now logs and shows a one-line notice in the status strip (`StatusBarView.showNotice`, detail in the tooltip, clears after 12 s) — never modal. The EMU save/restore-state errors and SourceList's "No windows found" are window sheets (`NSView.presentNonBlockingNotice`), and the launch-time catalog alert is a strip notice too. The remaining `runModal()` calls are user-initiated open/save panels and confirmation prompts. Regression: `selfqa ui` "a failed load returns without blocking" (0.9 ms, no modal window) and "a failed load says so in the status strip".


Found because the soak never finished. `sample` of the stuck process showed the main
thread parked in `-[NSAlert runModal]` since minute zero:
`SoakSelfQA.run` → `ShellController.loadClip` (`ShellController.swift:97–106`) →
`presentNotice` (`ShellController.swift:1104–1110`) → `alert.runModal()`.

`loadClip` is, by its own doc comment, the single path for every clip load (library
double-click, drag onto a source, Load button). On any load failure it blocks the
main thread in a modal dialog until a human clicks OK. Mid-show that is a full
freeze of UI and every main-thread-driven part of the output, not a dropped frame —
and the dialog may be on a screen nobody is looking at. Triggers: a corrupt file, an
unsupported codec, no video track, or (seen here) a 4K HEVC clip refused with
"Cannot Decode" while three HD channels are already decoding.

It also means **the heavy soak produced no data**: it froze on the D-channel alert
before its timed loop began and sat there ~2 hours. Self-QA must never hit a modal.

**Fix shape:** replace the modal with a non-blocking notice (status-strip message or
sheet/non-modal panel), and never present modals from self-QA. Other `runModal()`
call sites (`grep -rn '\.runModal()' App/Sources`, 20 hits) are mostly user-initiated
open/save panels and are fine; `EmuBrowserView.swift:524,568` and
`SourceListView.swift:206` look like error notices worth the same review.

### S7 — HEVC tagged `hev1` is refused ("Cannot Decode"); the same stream tagged `hvc1` plays

**FIXED (2026-09-27, step 1):** the bundled libav has no HEVC decoder, so the libav fallback was not available. Probed instead: AVAssetReader still *demuxes* `hev1` (passthrough), and VideoToolbox decodes those samples once the format description is re-made with the `hvc1` codec type and the same hvcC extensions. `HEV1Reader` does exactly that (display-order reorder buffer, seeks drop the GOP lead-in, decodes at canvas size); `AVFClipDecoder` uses it for `hev1` tracks through its usual cache/seek logic. A stream with in-band-only parameter sets still fails and is logged with that reason. Fixture: `samples/motion-hev1.mov` (make-fixtures.sh). Regression: `AVFClipDecoderTests.testHEVCTaggedHev1Plays`.


Isolated with `selfqa decode` (which bypasses S6's alert): `D-4k-hevc.mov` (`hev1`,
from `hevc_videotoolbox`) → `reader refused to start: Cannot Decode`. A stream-copy
retag to `hvc1` (`ffmpeg -c copy -tag:v hvc1`) → loads; open 11 ms, first frame
103 ms, steady 4.4 ms (worst 15 ms). So it is not a load/session limit — it's the
fourcc. `hev1` is legal HEVC and common from ffmpeg/cameras; AVFoundation's reader
refuses it. Combined with S6, dropping such a file mid-show freezes the app.
Fix shape: detect `hev1` at open and fall back to the libav path (as DV/MPEG already
use), or at minimum name the cause in the notice.

## Session 2026-09-27 (Opus) — the `selfqa import` dropped frame: FIXED

- **Cause:** found with a new in-process sampler, `MainThreadSampler`, opt-in with
  `VIDEOBOY_MAIN_SAMPLER=1`. `sample(1)` from the agent shell produced no call stacks,
  so the sampler was built into the app. The long stretches came from AppKit's
  display-link commit: `NSCollectionView` rebuilding library tiles
  (`LibraryGridView … itemForRepresentedObjectAt`). All three library grids reloaded
  on every library change, which during a scan is every 80 ms, at 25–35 ms of layout
  per rebuild.
  - The check's own "layout passes over 10 ms: 0" missed this because that commit
    runs in CoreAnimation's display-link observer, not the before-waiting observer
    the check watches.
- **Fix:**
  - `LibraryGridView.reload` updates the visible tiles in place when the list of
    entries is unchanged.
  - While an import is running, each library panel rebuilds at most every 0.35 s, and
    the three panels never rebuild within 0.1 s of each other. Outside imports,
    searching, sorting and single drops still update at once.
  - Batched `insertItems` was tried first; its own bookkeeping cost as much as a full
    rebuild.

## Session 2026-09-27 (Opus) — F9 FIXED: loading a clip no longer blocks the main thread

- **Cause, in two parts:**
  1. Opening a clip (file open, probe, the first reader or VideoToolbox start) ran
     on the main thread.
  2. Ejecting or replacing a clip freed the old decoder and its frame cache on the
     main thread; for 4K that is tens of MB.
- **Fix:**
  - `ClipSourceNode.load` is split into `prepare`, which does the opening and can run
    on any thread, and `install`, which swaps the clip in on main.
    `Engine.loadAsync` prepares on a serial `videoboy.clip-open` queue. The channel
    keeps playing its old clip until the new one is ready; a newer load for the same
    channel beats an older one.
  - `ShellController.loadClip` finishes the panel work in the load's completion. The
    Up Next advance and ADV's pause/re-cue now run after the new clip is in.
  - Replaced or ejected decoders are released on `videoboy.clip-retire`.
  - `VIDEOBOY_BLOCKING_LOAD=1` switches back to loading on the main thread.
  - Offline renders and Core tests keep the synchronous `load` (prepare + install).
- **Measured,** 3-min HD soak (2× 1080p H.264, ProRes, 4K HEVC), release build:

| Action (main thread) | Before (12-min soak) | After |
|---|---|---|
| drop clip, mean / worst | 14.05 / 19.27 ms | **0.09 / 0.22 ms** |
| eject + reload, mean / worst | 22.88 / 49.98 ms | **5.92 / 6.67 ms** |

  The soak passes every check, including "no performer action blocks the main
  thread for longer than a frame". 0 dropped of 5,395; worst tick 17.5 ms.
- **Gates:** `verify.sh` exit 0 (856 Core tests); `library`, `ab-roll`, `import`,
  `stress`, `import-mode`, `modes`, `push-fade` and `bars` pass. `audit` fails only
  on L3.
- **Test changes:** checks that read a channel straight after a drop now wait for
  `Engine.loadsInFlight` to reach 0 (`UISelfQA.waitForLoads`).
- One `import-mode` run read 36.7 ms. The next 3 runs read 14.0–14.2 ms, so it looks
  like a one-off; I'm watching it.

## Session 2026-09-27 (Opus) — ADV: zero-wait cuts, pre-opened clips

- **The ask (owner):** "ZERO stutter or delay when cutting to next clip. They need to
  be pre-loaded, ready to go when they are in the queue."
- **Before:** ADV picked and opened the next clip at the moment a take landed. The
  open was off the main thread (F9), but HD/4K takes 50–200 ms, so a quick cut could
  arrive before the channel was ready.
- **Now:**
  - Each channel's next ADV clip is **planned and opened in advance**. Planning
    happens when ADV is switched on, after every take (for the channel now on air,
    which leaves next), and when a queue changes. It uses copies of the queue and the
    shuffle state, so nothing is consumed early.
  - At the take the plan is committed and the pre-opened clip, already decoding its
    first frames, is swapped in. The work at the take is 0.2–1 ms (install 0.07–0.18,
    bookkeeping 0.08–0.28, next plan 0.4–0.8).
  - A stale plan (queue edited, fallback changed, a different clip on air) falls back
    to the old path. A plan still valid is kept, so a shuffle doesn't open a second
    clip.
  - Work around the take:
    - Panel work after an ADV swap moves to the next run-loop turn.
    - Source Controls is no longer moved to the off-air channel, and is rebuilt only
      if what it shows changed.
    - The Up Next list drops the played row instead of rebuilding.
- **Found and fixed on the way (affects every preview):**
  - `MetalPreviewView.present` could block the render tick in `nextDrawable()` when
    no drawable was free. The in-process sampler caught 27–35 ms stretches, and once
    1.1 s, all inside `nextDrawable`.
  - Each in-window preview now counts its drawables in flight and **skips a refresh
    rather than block** when none is free. The output window (display-synced) is
    exempt.
- **Gates:**
  - `verify.sh` exit 0 (868 Core tests).
  - `selfqa ab-roll`, new HD/4K section, run 4 times: **8 of 8 takes instant (0 opened
    at the take), 8 of 8 incoming clips rolled at once with 0 held frames, 0 dropped

## Session 2026-09-27 (Opus) — FIT / FILL / STRETCH / CENTRE now change the FEED

- **Owner report:** "Fit, Fill, Center do not work properly. They only change
  DISPLAY, but not the feed."
- **Cause:**
  - The source panel's key set only the monitor's `fillMode` and the saved default.
    `ClipSourceNode.framing`, which the GPU fitter uses to place the picture in the
    canvas, was never set, so the feed stayed Fit.
  - Centre was also silently treated as Fit in the feed.
  - Camera and captured-window sources weren't fitted at all: they entered the mix at
    their own size and were stretched.
- **Fix:**
  - The key calls `Engine.setFraming(_:channel:)`, which sets the clip node's framing
    and, for a camera/capture channel, the capture node's.
  - **Centre is real now:** native size, centred, unscaled (`nativeHeight` from the
    decoder), so a 1080p clip shows its middle at 1:1.
  - `CaptureSourceNode` fits through `CanvasFit` like clips do.
  - The source monitor always shows the feed as it is, instead of re-cropping it.
  - Framing is saved per channel in templates.
- **Known limit:** Centre on an HD clip is a little soft. Clips are decoded no larger
  than the canvas needs, so a 1:1 crop is upscaled. A sharp Centre would need decoding
  at full size while Centre is on.
- **Gates:**
  - `verify.sh` exit 0 (870 Core tests, 2 new for the placements).
  - New `selfqa framing` 5/5, reading back channel A **and the A/B sub-mix** for each
    mode (PNGs in `selfqa/out/perf/framing/`).
  - `bars`, `fullscreen`, `stress`, `template`, `ab-roll` and `library` pass; `audit`
    fails only on L3.
