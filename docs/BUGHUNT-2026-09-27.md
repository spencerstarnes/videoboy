## New findings (not in AUDIT-2026-09-26.md)

### S1 — The catalog's launch cost is invisible to the one screen built to show launch cost

`LaunchWindowController.swift` exists specifically so no part of startup reads as a
hang: its own header says "showing what is happening turns that pause into
information rather than a hang," and its `Extend` note is explicit — "add a
`LaunchStage` case and report it at the right moment." Its `LaunchStage` enum has
eight cases: metal, shaders, codecs, graph, clock, midi, displays, interface.
**There is no catalog/library stage.**

`AppDelegate.applicationDidFinishLaunching` (`AppDelegate.swift:56–58`) calls
`openCatalog(into:)` between `codecs` completing and `graph` completing. That call
chain is synchronous and unbounded by design:

- `Catalog.init` (`Catalog.swift:108–138`) does `flock`, `sqlite3_open_v2`, a
  migration, and — once a week — `backUpIfDue`'s `VACUUM INTO`, which does a full
  page-by-page copy of the whole catalog file (`Catalog.swift:316–347`).
- `LibraryModel.attach` (`LibraryModel.swift:252–276`) then does a synchronous
  `catalog.loadClips()` — `SELECT … ORDER BY position` over every row, allocating a
  `CatalogClip` per row — still on the main thread, still before `graph` lights up.

Both costs scale with library size, and neither is capped. For the 1,000-clip
library the 0.4.7 import test built, this is probably fast enough to be invisible in
the good sense. But the catalog is meant to accumulate for years (that's the entire
point of 0.4.7 — "the library a performer builds is the library they come back
to"), and unlike every other stage in this window, nothing here gets slower and then
tells you why. On the one day a week the backup fires *and* the library is large,
launch will pause between "DV codec" and "Render graph" with every dot still grey —
structurally indistinguishable from the hang this screen was built to rule out.

**Fix shape:** add `case library = "Library catalog"` to `LaunchStage`, report it
around the `openCatalog` call, and — separately worth a backlog line — move
`backUpIfDue`'s `VACUUM INTO` off the launch path entirely (it doesn't need to block
opening the catalog for writing; it could run after `graph`/`interface` complete, or
on a background queue with the UI already up).

**Severity:** low today, grows with every library import. Not in AUDIT-2026-09-26.md
(L1–L10 don't mention the catalog's launch path; the audit's own R1–R3 UI-cost
findings are about the library browser, not startup).

### Concurrency review of the frame path (the one thing AUDIT-2026-09-26.md admitted it skipped)

The audit's own game plan, item 3, flags "a per-source background decoder with a
prefetch ring... concurrency on the frame path, so it gets its own review" and then
never does it. Ran that review (`ClipPrefetcher`, `AVFClipDecoder`, `ClipDecoders`,
`DVDecoder`, `MPEGStreamDecoder`, `ClipSourceNode`, `Engine`, `TextureUploader`, read
in full, not excerpted).

**Headline: the prefetcher itself is clean.** `ready`/`wanted`/`urgent`/`pumping` are
all read-modify-written under one `NSLock` acquisition each (no check-then-act
splits), every recursive `queue.async` captures `[weak self]` so an ejected clip's
pump chain self-terminates, `ImageBuffer` is a value type so frames crossing the
decode-queue/main-thread boundary can't be mutated from under a reader, and a
swapped clip gets a wholly separate `ClipPrefetcher` object rather than mutated
shared state — so there's no stale-completion class of bug to find because there's
no shared mutable state for a stale completion to land in. No data races, no
deadlocks, no retain cycles found in the hot path.

Three smaller things, none of them frame-path stutter risks:

### S2 — `av_log_set_level` is an unguarded write to libav's global log level

`MPEGStreamDecoder.swift:115` calls `av_log_set_level(AV_LOG_QUIET)` inside
`init()`, which runs on whichever thread opens a clip — a channel's own decode
queue, *or* `ClipDecoders.duration(of:)` called from the background `ImportJob`
while scanning a folder of `.m2v`/`.mpg` files (CLAUDE.md: imports run off the main
thread). Two clips opening concurrently — an import batch scanning MPEG files while
a live channel loads one — write this process-global from different threads with no
synchronization. **Failure scenario:** worst case is a transiently wrong log level
(FFmpeg chatter briefly reappears in the log, or vice versa); it's C global state
with no memory-safety consequence, not a crash. Fix: call it once at process start
(a `static let` token), not per-decoder-init.

### S3 — `ClipPrefetcher.image(at:damage:)` has a latent reentrancy deadlock

`ClipPrefetcher.swift:100`'s unbounded-wait entry point (used by `renderToImage` and
self-QA) does `queue.sync { decoder.image(...) }`. Safe today — nothing that runs
*on* `queue` currently calls back into this method on the same prefetcher. But
GCD's serial-queue reentrant `sync` hangs forever, and there's no guard against it:
a future decoder that lazily opens a second clip and asks its own prefetcher for a
frame mid-decode, or a self-QA helper invoked from a callback already queued on
`queue`, would deadlock the process permanently. **Failure scenario is entirely
hypothetical today** — flagging it because it's a landmine for the *next* person to
touch this file, not a live bug. Fix: a comment stating the invariant, plus
`dispatchPrecondition(condition: .notOnQueue(queue))` in debug builds.

### S4 — Core is Swift 6 tools, Swift 5 language mode, on purely manual concurrency

`Core/Package.swift` declares `swift-tools-version: 6.0` but every target opts into
`.swiftLanguageMode(.v5)` (lines 47, 53, 59). Combined with `ClipPrefetcher` using
raw `DispatchQueue`/`NSLock`/`DispatchSemaphore` with zero `Sendable`/actor
annotations, none of the correctness described above is compiler-enforced — it's
correct because this review (and whoever wrote it) reasoned carefully about it, not
because the compiler would catch a regression. Not a bug; a note that if S2/S3-class
issues are worth closing structurally rather than by convention, `ClipPrefetcher`
would need real Swift 6 concurrency checking (`@unchecked Sendable` at minimum, with
the file's own `THREADING` comment turned into an enforced contract).

**None of S2–S4 change the "safe today" verdict on the frame path.** Given how
carefully AUDIT-2026-09-26.md's F1–F9 already dissects this exact code for
performance, this — a mostly clean concurrency bill of health — is itself the
useful new information: the audit's open "needs its own review" item can be closed
as reviewed, with S2/S3 as small, non-urgent follow-ups.
